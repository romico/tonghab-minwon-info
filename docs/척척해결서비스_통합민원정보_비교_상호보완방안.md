# 도로이용불편 척척해결서비스와 전주시 통합민원정보 비교 및 상호보완 방안

> 작성 기준: 2026-10-22  
> 목적: 타 지자체 공무원 대상 발표에서 기존 국토교통부 서비스와 전주시 통합민원정보의 역할을 정확히 구분하고, 중복 구축이 아닌 상호보완 방향을 설명하기 위한 자료

## 먼저 구분할 점

첨부 화면의 **‘도로이용불편 척척해결서비스’ 앱은 시민이 불편사항을 신고하고 처리 결과를 확인하는 프론트엔드**입니다. 국토교통부가 안내하는 척척해결서비스의 업무 흐름은 접수된 신고를 해당 도로관리기관에 전달하고, 접수·이관 및 처리 결과를 신고자에게 알려주는 것입니다. 전주시 안내도 사진·위치정보와 함께 신고하고 담당기관 이관 및 처리 결과를 앱에서 확인하는 절차를 설명합니다.[1][2]

**전주시 통합민원정보는 이 시민 신고 앱과 같은 제품이 아닙니다.** 현재 저장소에서 확인되는 기능은 생활민원 관리대장과 내부 현황·보고를 지원하는 로컬 우선 업무 도구입니다. 시민 공개 신고 앱이나 척척해결서비스 연계 기능으로 확인되지는 않습니다.[3][4]

아래의 ‘국토교통부 서비스 업무체계’는 공개 안내에서 확인되는 접수·기관 이관·결과 안내 역할을 뜻합니다. 내부 시스템의 기술 아키텍처, 별도 중앙 백엔드의 구성, 외부 연계 API 제공 여부는 공개된 자료만으로 확인하지 못했으므로 단정하지 않습니다.

## 기능·역할 비교

| 비교 항목 | 척척해결서비스 앱 — 시민 프론트엔드 | 국토교통부 척척해결서비스 — 업무·처리 체계 | 전주시 통합민원정보 — 내부 업무지원 |
|---|---|---|---|
| 핵심 역할 | 시민이 도로 이용 불편을 신고하고 진행·결과를 확인하는 모바일 접점 | 신고를 접수해 담당 도로관리기관으로 이관하고 처리 상태·결과를 알리는 업무 흐름 | 민원 원천 정보를 내부 관리대장으로 관리하고 현황·보고를 집계 |
| 주 사용자 | 도로 이용 시민 | 국토교통부·관계기관 및 도로관리기관의 처리 담당자, 신고 시민(결과 확인) | 지자체 민원 담당자·보고 작성자·관리자 |
| 주 대상 | 포트홀, 낙석·낙하물, 도로시설물 등 도로 이용 불편. 첨부 화면에는 로드킬, 배수시설, 시설물, 포트홀 등 신고 항목이 보임 | 앱으로 들어온 도로 불편 신고의 접수·담당기관 이관·처리결과 통지 | 생활민원 관리와 부서별 현황·총괄표·일일보고 등 내부 보고 |
| 입력 정보·행위 | 신고 내용, 사진, 위치정보 등을 등록하거나 위치 기반 담당기관 전화 연결 | 신고를 담당기관의 처리 흐름으로 전달하고 접수·이관·처리결과를 알림 | 담당자가 민원 정보를 입력·수정하거나 HWPX 카드에서 초안을 가져와 검수 후 등록 |
| 주요 산출물 | 신고 접수 및 ‘나의 민원’에서 확인하는 상태·결과 | 담당 도로관리기관으로의 이관과 처리결과 회신 흐름 | 내부 관리대장, 집계 화면, Excel 보고서, 보고 스냅샷 |
| 기준 데이터의 관점 | 개별 시민 신고와 그 신고의 처리 경과 | 해당 도로 민원의 기관 간 처리·회신 | 기관 내부에서 관리하는 생활민원 원천과 이를 바탕으로 한 집계 |
| 시민 접점 | 있음 — 시민 신고 앱 | 있음 — 앱 신고의 접수·이관·결과 안내를 포함하는 서비스 흐름 | 현재 확인된 범위에서는 없음 — 내부 업무지원 용도 |
| 운영 범위·형태 | iOS·Android 앱으로 안내됨 | 도로관리기관으로 신고를 전달하고 처리결과를 회신하는 공공 업무체계 | 저장소 기준 단일 PC·단일 관리자 중심의 로컬 우선 구성 |
| 현재 확인된 상호연계 | 전주시 안내는 앱 신고가 담당기관으로 전송·이관되고 결과를 앱에서 확인한다고 설명 | 특정 지자체 내부 시스템과 자동 동기화되는 방식은 공개 자료에서 확인되지 않음 | 척척해결서비스와 자동 API 연계·동기화하는 구현은 저장소에서 확인되지 않음 |

**핵심은 두 개의 ‘척척해결서비스’ 항목을 별도 제품 두 개처럼 과장해 나누지 않는 것입니다.** 시민 앱은 접수·조회 인터페이스이고, 국토교통부 서비스는 공개 설명으로 파악되는 접수·이관·결과 안내 흐름입니다. 내부 구성요소가 실제로 어떻게 분리·연계되어 있는지는 별도 확인이 필요합니다.

## 상호보완적 활용 흐름 제안

| 단계 | 주 담당 서비스 | 권장 역할 | 설계 시 주의점 |
|---|---|---|---|
| 1. 시민 신고 | 척척해결서비스 앱 | 시민은 기존 앱에서 도로 불편을 사진·위치와 함께 신고하고 접수 내역을 확인 | 별도 지자체 앱으로 같은 신고를 다시 받는 구조를 우선 만들지 않음 |
| 2. 기관 접수·분배 | 국토교통부 척척해결서비스 업무 흐름 | 신고를 해당 도로관리기관으로 전달하고 접수·이관·처리결과를 시민에게 안내 | 담당 도로관리청과 실제 이관·회신 규칙을 확인하고, 국토부 서비스가 공식 접수·상태의 기준인지 합의 |
| 3. 시 내부 업무 추적 | 전주시 통합민원정보 — 제안된 보완 활용 | 시 담당부서의 내부 업무량·처리 현황·후속조치가 필요할 때 공식 접수 건을 내부 관리 기준에 맞춰 추적 | 현재 자동 연계 기능으로 표현하지 말 것. 수기·파일 이관 등 임시 절차를 정할 경우 중복 입력·불일치 책임을 명시 |
| 4. 상태·결과 확인 | 국토부 서비스 + 시 내부 절차 | 시민에게 제공되는 공식 처리결과는 기존 척척 앱 흐름을 우선 존중하고, 내부 시스템은 내부 업무 관리·보고에 활용 | 두 시스템에서 서로 다른 ‘처리 완료’ 상태가 발생하지 않도록 상태 정의·갱신 책임을 합의 |
| 5. 분석·업무개선 | 전주시 통합민원정보 — 데이터 연계가 승인된 경우 | 비식별 또는 필요한 최소 범위의 집계로 유형·부서·기간별 업무량과 반복 문제를 분석 | 제공 근거·목적·보존기간·접근권한을 정하고, 신고자 개인정보·사진의 중복 저장을 최소화 |

### 권장 운영 모델

1. **시민 신고 창구는 기존 척척해결서비스를 우선 안내합니다.** 전주시 웹 안내·민원 안내문·현장 QR 등으로 앱 신고 경로를 알려 중복 앱 구축과 이중 신고를 피합니다.
2. **국토부·도로관리기관의 공식 접수번호와 상태를 기준으로 삼을지 먼저 합의합니다.** 통합민원정보에 별도 내부 추적이 필요하다면 원 접수번호, 접수 출처, 담당 부서, 내부 후속조치 등을 연결하는 업무 규칙을 정합니다. 이는 현재 확인된 기능이 아니라 도입 전 설계 제안입니다.
3. **연계가 없으면 자동 동기화처럼 발표하지 않습니다.** API나 승인된 데이터 제공 절차를 확인하기 전에는 수기 입력·파일 전달 등 임시 절차의 필요성과 위험을 솔직하게 밝힙니다.
4. **상태의 권위(authoritative source)를 하나로 정합니다.** 시민에게 통지된 결과와 시 내부의 후속 작업 메모를 구별하고, 담당자가 두 시스템을 각각 갱신해야 하는지 여부를 사전에 정합니다.
5. **사진·위치·신고자 정보는 필요한 범위만 처리합니다.** 내부 보고에 개인 단위 상세정보가 필요하지 않다면 집계 결과나 최소 식별정보만 활용하고, 보존·파기와 권한 정책을 기관 검토에 맡깁니다.
6. **성과는 실제 업무 흐름을 측정한 뒤 설명합니다.** 이관 후 내부 재입력 건수, 담당부서 배정 소요시간, 처리 상태 불일치, 보고서 작성·수정시간 등을 정의해 시범 운영 전후로 비교합니다. 측정 전에는 시간 절감이나 오류 감소를 성과 수치로 주장하지 않습니다.

## 발표에서 사용할 비교 메시지

> “척척해결서비스는 시민이 도로 불편을 신고하고 담당 도로관리기관의 처리결과를 확인하는 기존 채널입니다. 전주시 통합민원정보는 그 신고 앱을 대체하는 서비스가 아니라, 지자체 내부의 생활민원 관리와 현황·보고를 지원하는 도구입니다. 두 시스템의 자동 연계는 현재 확인된 기능이 아니므로, 기존 접수 흐름을 유지하면서 내부 중복입력과 상태 불일치를 줄일 수 있는 업무 절차부터 검토해야 합니다.”

## 예상 질문과 짧은 답변

**“국토교통부 앱이 있는데 왜 또 만듭니까?”**  
“시민 신고 창구를 새로 만들려는 것이 아닙니다. 기존 앱의 신고·결과 안내와 지자체 내부의 관리·보고를 구분합니다. 다만 실제 내부 중복입력이 있는지는 현행 업무 흐름을 확인한 뒤 개선 과제로 삼겠습니다.”

**“두 시스템은 이미 자동으로 연동됩니까?”**  
“현재 확인한 저장소와 공개 안내 자료만으로는 자동 연계를 확인하지 못했습니다. 연계 API, 데이터 제공 근거와 담당기관 협의가 확인되기 전까지는 연계된다고 말하지 않겠습니다.”

**“통합민원정보가 척척해결서비스의 처리결과를 시민에게 알려줍니까?”**  
“그 기능은 현재 확인되지 않았습니다. 시민 대상 접수·결과 확인은 기존 척척해결서비스 안내 흐름을 기준으로 보고, 통합민원정보는 내부 업무관리·보고 역할로 구분하는 것이 맞습니다.”

**“도로 민원은 전부 통합민원정보에 넣어야 합니까?”**  
“그렇게 정해져 있지 않습니다. 공식 접수·기록 체계와 중복 저장 필요성을 기관이 먼저 검토해야 합니다. 내부적으로 추적할 필요가 확인된 최소 항목만 책임 주체와 함께 정하는 것이 바람직합니다.”

- [ ] 척척해결서비스의 접수번호, 이관·완료 상태, 처리결과를 시 내부 시스템에 전달하는 공식 절차나 API가 있는가?
- [ ] 전주시 담당자가 현재 접수 건을 다른 대장이나 시스템에 재입력하는지, 실제로 중복 입력이 발생하는가?
- [ ] 전주시 통합민원정보에 척척 앱 신고가 현재 등록·연계되고 있는가? 확인하지 못했다면 미연계로 표현했는가?
- [ ] 시민에게 통지되는 공식 처리 상태와 시 내부 추적 상태의 책임자를 구분했는가?
- [ ] 사진·위치·신고자 정보의 2차 이용, 공유, 보존·파기 근거를 기관 담당자와 검토했는가?
