# 개인정보 저장 보안 정책 (초안)


| 항목    | 내용                                                                                          |
| ----- | ------------------------------------------------------------------------------------------- |
| 문서 유형 | 보안 정책 / 설계 의사결정                                                                             |
| 대상    | 통합민원정보 (`tonghab-minwon-info`) 로컬 SQLite                                                    |
| 상태    | **S1·TOTP 구현됨**                                                                            |
| 관련    | [기획서 §11](./통합민원정보%20서비스%20기획서.md) · [사진·민원카드 정책](./photo-hwpx-policy.md) · [ERD](./erd.md) |


> **한 줄 요약:** 민원인 성명·연락처·사진은 DB에 AES-256-GCM으로 저장되고, 로그인 시 잠금 해제됩니다. 선택적으로 TOTP 2FA를 켤 수 있습니다. 화면 마스킹과 저장 암호화는 서로 대체되지 않습니다.

---

## 1. 왜 필요한가

이 앱은 Windows 포터블로 `data/tonghab-minwon.db` 파일을 PC·USB에 둡니다.


| 위험          | 예시                   | 현재 방어                |
| ----------- | -------------------- | -------------------- |
| DB 파일 유출    | 폴더 복사, 백업 공유, 분실 USB | 없음 (평문)              |
| 비인가 PC 열람   | sqlite3로 파일 직접 열기    | 없음                   |
| 로그인 우회 열람   | API 없이 DB만 열기        | 로그인과 무관              |
| 화면/엑셀 과다 노출 | 모니터·공유 파일            | **마스킹**(표시용, 저장과 별개) |


로그인·세션은 **네트워크 API 접근**만 막습니다. **디스크上的 DB 파일**은 막지 않습니다.  
개인정보 보호를 위해 **저장 시점 암호화**가 필요합니다.

| -------------------------- | --------------------------------------------- |

| `audit_logs`               | 요약 위주. 원문 전화/이름 금지 유지                         |




### 2.3 민원 `content` / `location` / `remark`

자유 텍스트라 이름·전화가 들어갈 수 있습니다.


| 단계        | 정책                           |
| --------- | ---------------------------- |
| 1단계 (MVP) | 평문 유지 + 운영 안내(내용에 연락처 기입 자제) |
| 2단계       | 필요 시 동일 키로 필드 암호화 또는 탐지 경고   |

## 3. 현재 vs 목표


| 계층    | 현재        | 목표                      |
| ----- | --------- | ----------------------- |
| DB 파일 | 평문 SQLite | 개인정보 필드(또는 DB 파일) 암호문   |
| 비밀번호  | scrypt 해시 | 유지 + (선택) 암호 키 파생에 사용   |
| 화면    | 기본 마스킹    | 유지 (복호화 후 표시 시 마스킹)     |
| 엑셀    | 선택 마스킹    | 기본 마스킹 + 원문 시 감사        |
| 전송    | localhost | 당분간 동일 (원격 공개 시 TLS 별도) |


**원칙:**  

- **마스킹** = 사람이 볼 때 가리기  
- **암호화** = 파일을 훔쳐도 읽기 어렵게 하기  
둘 다 필요하며 서로 대체되지 않습니다.

## 4. 권장 기술 방향 (의사결정)

로컬·단일 관리자·포터블 환경에서는 아래 **A안을 1순위**로 권합니다.

### A안 — 필드 단위 암호화 (권장 MVP)

- 알고리즘: **AES-256-GCM** (Node `crypto`)
- 대상: `complainantName`, `complainantPhone`, (권고) 사진 payload
- 저장 형태 예: `enc:v1:<iv>:<tag>:<ciphertext>` (Base64)
- 키: 관리자 비밀번호에서 **scrypt/PBKDF2로 파생**한 DEK(데이터 키), 또는 별도 “데이터 잠금 비밀번호”
- 복호화: 로그인 성공 후 서버 메모리에만 키 유지, 프로세스 종료 시 소멸
- 검색: 암호화 필드는 **정확 일치 검색만** 가능하거나, 평문 검색은 복호화 후 메모리에서 (초기에는 이름/전화 검색 제한 명시)

**장점:** Node 내장만으로 가능, SQLCipher 네이티브 의존 없음, 포터블 배포와 맞음.  
**단점:** DB를 열면 “어떤 건이 있는지” 등 비개인 메타는 보임. 키·비밀번호를 잊으면 복구 불가.

### B안 — DB 파일 전체 암호화 (SQLCipher 등)

- DB 통째 암호화
- **장점:** 구현 개념이 단순, 파일 유출 시 전체 보호  
- **단점:** `node:sqlite`와 바로 안 맞음, 네이티브 모듈·포터블 빌드 복잡도 증가

→ **1차는 A안**, 추후 필요 시 B안 재검토.

### 하지 말 것

- 소스코드·설정 파일에 고정 암호키 하드코딩
- 키를 `localStorage`에 평문 저장
- “마스킹만 하면 암호화한 것”으로 간주
- 감사 로그에 복호화된 전화·이름 기록

## 5. 키·비밀번호 운영 규칙


| 규칙      | 내용                                                            |
| ------- | ------------------------------------------------------------- |
| 키 보관    | 디스크에 평문 키 파일 두지 않음. 로그인(또는 데이터 잠금 해제) 시에만 메모리 보유              |
| 비밀번호 분실 | **복구 불가**를 UI·매뉴얼에 명시. 백업본+비밀번호만 복구 수단                        |
| 비밀번호 변경 | 기존 DEK를 새 비밀번호로 재래핑(re-wrap) 또는 전 필드 재암호화 절차 필요               |
| 백업      | `tonghab-minwon.db` 백업 = 암호문 백업. 비밀번호 없이 복원해도 개인정보는 읽히지 않아야 함 |
| 기본 계정   | `admin/admin`은 **최초 설치 직후 변경 필수**. 변경 전까지 암호화 미활성 또는 경고       |
| 개발/샘플   | 시드 데이터의 가짜 전화는 암호화 파이프라인과 동일하게 처리해 경로를 검증                     |


### 5.1 2단계 인증(2FA) — 적용 가능

**결론: 가능합니다.** 현재는 아이디·비밀번호 + 세션 쿠키만 있습니다. 그 위에 두 번째 요소를 붙일 수 있습니다.

| 방식 | 이 앱(로컬·포터블) 적합성 | 비고 |
|---|---|---|
| **TOTP** (Google/Microsoft Authenticator 등) | **권장** | SMS·메일 서버 불필요, 오프라인 가능 |
| SMS / 이메일 OTP | 비권장 | 통신·외부 서비스 의존, 포터블과 안 맞음 |
| FIDO2 / 보안키 | 가능하나 과함 | 단일 관리자·로컬에는 부담 |

**로그인 흐름(권장):**  
1) 아이디·비밀번호 검증 → 2) 아직 세션 발급 전, OTP 입력 화면 → 3) TOTP 검증 후 세션 쿠키 발급.

**설정:** QR로 TOTP 시크릿 등록, 일회용 복구 코드(평문 1회 표시 후 해시 저장), 설정에서 켜기/끄기(끄기는 비밀번호+현재 OTP 확인).

**2FA가 막는 것 / 못 막는 것**

| 막음 | 못 막음 |
|---|---|
| 비밀번호만 알아도 앱 로그인 | DB 파일을 직접 열어 평문 열람 → **at-rest 암호화**가 담당 |
| 자리 비운 PC에서 단순 로그인 시도 | 이미 로그인된 세션(별도 잠금·짧은 TTL로 보완) |

→ **DB 암호화(S1)와 2FA는 보완 관계**입니다. 파일 유출 대비는 암호화, 계정 도용·원격/공유 PC 로그인은 2FA.

**구현 부담:** `otplib`(또는 동등) + `users`에 `totp_secret`(암호화 저장 권고)·`totp_enabled`·복구 코드 해시. 네이티브 모듈 불필요, 포터블과 충돌 적음.

## 8. 수용 기준 (구현 시)

1. `tonghab-minwon.db`를 외부 도구로 열었을 때 `complainantName`/`complainantPhone`이 **평문으로 보이지 않는다**.
2. 정상 로그인 후 앱에서는 기존과 같이 업무 가능(마스킹 기본).
3. 잘못된 비밀번호로는 API·복호화 실패, 추측 가능한 에러로 키 길이 등을 노출하지 않는다.
4. 백업 파일을 비밀번호 없이 복사해도 개인정보 평문이 나오지 않는다.
5. 마이그레이션 후 구 평문 필드가 DB에 남아 있지 않다(또는 재암호화 완료 플래그로 검증).

## 9. 책임·용어


| 용어               | 의미                               |
| ---------------- | -------------------------------- |
| 암호화 (encryption) | 키 없이 원문 복원 불가                    |
| 해시 (hash)        | 비밀번호 검증용 일방향 (복호화 없음)            |
| 마스킹 (masking)    | UI/파일에서 일부만 가림 (원문은 别处에 있을 수 있음) |
| at-rest          | 디스크에 저장된 상태의 보호                  |
| in-transit       | 네트워크 전송 구간 보호 (현 단계는 localhost)  |



| 역할           | 책임                        |
| ------------ | ------------------------- |
| 운영 담당        | 비밀번호 관리·백업·초기화 승인         |
| 개발           | S1 구현·마이그레이션·테스트          |
| (조직) 정보보호 담당 | 본 정책과 기관 개인정보 처리방침 정합성 검토 |

## 10. 구현 결정 사항 (반영됨)

1. **A안(필드 AES-GCM)** 으로 MVP 진행
2. 암호 키는 **로그인 비밀번호에서 파생**
3. **사진**도 1차에 암호화
4. 비밀번호 분실 시 **복구 없음** (설정·로그인 화면에 고지)

구현: `server/field-crypto.ts`, `server/vault.ts`, `server/totp.ts`, `server/auth.ts`, `server/db.ts`, 설정·로그인 UI. 스모크: `npx tsx scripts/smoke-security.ts`
