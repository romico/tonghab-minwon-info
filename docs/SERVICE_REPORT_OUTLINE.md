## 1. 보고서 전체 방향

이 보고서는 현재 구현된 서비스를 단순히 기능 목록으로 소개하지 않습니다. **기존 민원 보고 업무의 문제를 어떻게 해결하고 있으며, 다음 단계에서 무엇을 우선 개발해야 하는지**를 근거와 함께 설명하는 의사결정용 문서로 구성합니다.

보고서의 핵심 결론은 다음 한 문장으로 요약합니다.

> 통합민원정보는 관리대장을 단일 원천으로 삼아 민원 입력과 보고서 생성을 일관되게 만들었으며, 다음 단계에서는 보고 기준일·보고 결과 보존·개인정보 다운로드 통제를 강화해야 합니다.

## 3. 보고서 목차 구성안

### 표지

**표제:** 통합민원정보 서비스 분석 및 발전 방향

**부제:** 전주시 생활민원 데이터 관리·보고 업무의 표준화와 신뢰성 강화

표지에는 서비스명, 분석 기준일, 작성 부서 또는 작성자를 표시합니다. 실제 운영 데이터나 개인정보가 포함된 화면은 표지에 사용하지 않습니다.

### 목차

본문의 장·절 번호와 페이지를 표시합니다. 본문은 다음 흐름을 유지합니다.

```text
요약
  → 업무 배경과 문제
  → 현재 서비스 분석
  → 사용자와 업무 흐름
  → 기술·데이터 구조
  → 성과와 리스크
  → 발전 전략과 로드맵
  → 결론 및 의사결정 요청
```

## 4. 장별 상세 구성

### 제1장. 경영진 요약

#### 목적

보고서를 읽는 사람이 2~3분 안에 서비스의 필요성, 현재 성과, 다음 우선순위를 이해하도록 합니다.

#### 포함 내용

- 서비스 한 줄 정의
- 해결하려는 기존 업무 문제 3가지
- 현재 구현된 핵심 가치 3가지
- 가장 중요한 리스크 3가지
- Phase 1 우선 개발 항목
- 의사결정이 필요한 사항

#### 핵심 메시지

관리대장 하나를 기준으로 모든 보고서를 자동 집계하는 구조는 이미 갖춰져 있습니다. 이제 보고 기준과 결과 보존을 명확히 해야 행정 보고의 신뢰성이 완성됩니다.

#### 권장 시각화

| 시각 요소 | 표현 내용 |
|---|---|
| 핵심 메시지 박스 | 입력은 한 번, 집계는 일관되게, 보고는 검증 가능하게 |
| 3개 지표형 영역 | SSOT, 자동 집계, 로컬 포터블 운영 |
| 우선순위 표 | 보고일 선택기, Excel 마스킹, 내보내기 감사 |

### 제2장. 업무 배경과 문제 정의

#### 목적

서비스가 기존 Excel 업무의 어떤 비용과 오류를 줄이는지 설명합니다.

#### 포함 내용

- 기존 관리대장·부서별현황·총괄표·일일보고 운영 방식
- 수식·복사·수동 집계에 따른 문제
- 민원카드와 사진 재입력 문제
- 담당 PC별 실행 환경 차이
- 개인정보가 포함된 보고서 공유 위험
- 과거 보고 결과를 재현하기 어려운 문제

#### 분석 표준

문제는 기술 용어보다 업무 결과 기준으로 표현합니다.

| 업무 문제 | 발생 원인 | 영향 | 서비스 대응 |
|---|---|---|---|
| 보고서 숫자 불일치 | 여러 시트와 수식의 중복 관리 | 재검증·수정 시간 증가 | 관리대장 SSOT |
| 일일보고 작성 지연 | 수동 매트릭스 집계 | 보고 마감 부담 | 자동 집계 |
| 자료 재입력 | HWPX와 사진을 별도 입력 | 누락·오타 | HWPX 초안 가져오기 |
| PC 설치 부담 | Node·실행 환경 필요 | 배포 지연 | Windows 포터블 |

#### 권장 시각화

기존 방식과 개선 방식을 좌우 비교 다이어그램으로 표현합니다. 기존 흐름은 `여러 Excel → 수동 복사 → 보고서별 수정`, 개선 흐름은 `관리대장 → 자동 집계 → 4종 보고서`로 구성합니다.

### 제3장. 서비스 개요와 범위

#### 목적

현재 서비스가 제공하는 기능과 제공하지 않는 기능을 명확히 구분합니다.

#### 포함 내용

- 서비스 정의와 운영 범위
- 주요 기능: 대시보드, 관리대장, 부서별현황, 총괄표, 일일보고, 감사로그, 설정
- Windows 포터블과 로컬 SQLite 운영 방식
- 현재 사용자 모델: 단일 관리자 중심
- 비목표: 클라우드 멀티테넌시, 모바일 앱, 외부 접수 연계, RBAC

#### 권장 표

| 구분 | 현재 제공 | 현재 미제공 |
|---|---|---|
| 데이터 관리 | 민원 CRUD, HWPX 가져오기, 사진 | 외부 민원 채널 연계 |
| 보고 | 4종 화면 및 Excel 내보내기 | 보고 스냅샷·확정 API |
| 보안 | 세션 인증, 감사로그, 화면 마스킹 | 다중 역할 권한 관리 |
| 배포 | Windows 64비트 포터블 | 클라우드 멀티테넌시 |

### 제4장. 사용자와 업무 여정

#### 목적

기능 목록을 실제 사용자의 업무 흐름으로 번역합니다.

#### 포함 내용

- 민원 담당자 여정
- 보고 작성자 여정
- 관리자 여정
- 검토자·상급자 여정
- 현재 단일 `admin` 계정 중심 운영이라는 제약

#### 권장 사용자 여정

```text
로그인
  → 대시보드에서 현황 파악
  → 관리대장에 수동 등록 또는 HWPX 가져오기
  → 초안 검수 및 상태·부서 보완
  → 관리대장 저장
  → 부서별·총괄·일일 화면 확인
  → 개별 또는 통합 Excel 생성
  → 감사로그·설정 점검
```

#### 사용성 평가 기준

| 단계 | 현재 강점 | 개선 관점 |
|---|---|---|
| 입력 | HWPX 다중 가져오기 | 필드별 신뢰도와 검수 표시 |
| 집계 | 동일 원천 자동 반영 | 보고일과 통보일 구분 강화 |
| 보고 | 기존 양식 친화적 Excel | 생성 전 미리보기와 기준 표시 |
| 운영 | 감사로그와 포터블 배포 | 백업·복구 안내 및 도구화 |

### 제5장. 서비스 구조와 데이터 아키텍처

#### 목적

서비스의 신뢰성이 어떤 기술·데이터 구조에서 나오는지 설명합니다.

#### 포함 내용

- React + Express + SQLite 구성
- 브라우저, API 서버, DB 간 관계
- `Complaint` 기반 SSOT 구조
- `ComplaintStore`와 `aggregate.ts`의 파생 집계
- Excel이 브라우저에서 생성되는 방식
- HWPX 원본을 저장하지 않고 파싱하는 정책

#### 필수 구조도

```text
[관리자 브라우저]
       │
       ├─ 관리대장 CRUD / HWPX 검수
       ├─ 기간 필터·보고일 상태
       └─ 집계·Excel 생성
       │
       ▼
[Express API :8787]
       │
       ▼
[SQLite: complaints / users / sessions / settings / audit_logs]
```

#### 설명할 핵심 원칙

1. 관리대장만 쓰기 원천이다.
2. 부서별현황·총괄표·일일보고는 중복 테이블이 아니라 조회 시점 파생 결과다.
3. 통보일 기간은 필터 기준이고 보고일은 일일보고와 처리기간 계산 기준이다.
4. 로컬 바인딩과 파일 DB는 현장성을 높이지만 다중 사용자·복구·보안 측면의 제약을 만든다.

### 제6장. 현재 기능과 구현 수준

#### 목적

현재 코드와 문서를 기준으로 실제 구현 범위를 정리합니다.

#### 권장 기능 매트릭스

| 기능 영역 | 현재 구현 | 사용자가 얻는 가치 | 추가 보완 |
|---|---|---|---|
| 인증·세션 | HttpOnly 세션, TTL, 비밀번호 변경 | 기본 접근 통제 | RBAC·사용자 관리 |
| 관리대장 | CRUD, 검색·필터, 삭제 확인 | 원천 데이터 관리 | 대량 편집·품질 검증 |
| HWPX | 다중 가져오기, 초안 검수, 일괄 등록 | 재입력 감소 | 신뢰도 표시 |
| 집계 | 부서·총괄·일일·대시보드 | 보고 자동화 | 기준일 명시 |
| Excel | 개별·통합 내보내기 | 기존 양식 유지 | 기본 마스킹·감사 |
| 감사 | 로그인·CRUD·설정 이벤트 | 변경 추적 | 내보내기 이벤트 |
| 배포 | Windows 포터블 ZIP | 설치 부담 감소 | 백업·복구 도구 |

### 제7장. 성과, 한계와 리스크

#### 목적

현재 성과를 과장하지 않고, 운영에 영향을 주는 제약을 우선순위와 함께 제시합니다.

#### 강점

- 관리대장 SSOT로 데이터 정합성 확보
- 기존 행정 보고 양식과의 연속성
- HWPX 가져오기와 사용자 검수 흐름
- Windows 포터블 배포
- 인증·민원 변경·설정 변경 감사 기반

#### 주요 리스크

| 우선순위 | 리스크 | 영향 | 대응 필요 시점 |
|---|---|---|---|
| P0 | 보고일 선택 UI 부재 | 과거 일일보고 기준 불명확 | 즉시 |
| P0 | 보고 스냅샷 미구현 | 사후 결과 재현 불가 | 단기 |
| P0 | 통합 Excel 마스킹 부족 | 개인정보 공유 위험 | 즉시 |
| P1 | 사진 data URL 저장 | DB·요청 크기 증가 | 중기 |
| P1 | 단일 계정 | 역할 분리·책임 구분 제한 | 중기 |
| P2 | 자동화 테스트 부족 | 변경 회귀 위험 | 지속 |

#### 작성 원칙

리스크는 “문제가 있다”로 끝내지 않고, 현재 영향과 제안 대응을 함께 씁니다. 구현되지 않은 기능은 현재 제공 기능처럼 표현하지 않습니다.

### 제8장. 발전 전략과 목표 상태

#### 목적

현재 구조를 유지하면서 서비스 품질을 높이는 제품 전략을 제시합니다.

#### 3대 전략

1. **입력보다 보고 신뢰성을 우선한다.** 모든 보고 화면에 보고일, 통보일 기간, 대상 건수를 명시합니다.
2. **로컬 우선은 유지하되 데이터 이동성을 제품 기능으로 만든다.** 백업·무결성·복구 확인을 운영 기능으로 확장합니다.
3. **개인정보 보호를 다운로드 중심으로 강화한다.** 통합 Excel의 기본 마스킹, 원문 다운로드 경고, 감사 이력을 적용합니다.

#### 목표 상태

```text
원천 데이터 등록
  → 기준일·기간 확인
  → 집계 결과 미리보기
  → 개인정보 정책 확인
  → 보고서 생성
  → 생성 이력·스냅샷 보존
  → 필요 시 동일 결과 재조회
```

### 제9장. 단계별 개발 로드맵

#### 목적

개발 우선순위를 사용자 가치와 위험 감소 기준으로 설명합니다.

#### 로드맵 표

| 단계 | 목표 | 주요 기능 | 완료 판단 |
|---|---|---|---|
| Phase 0 | 기준·품질 정비 | 용어 통일, 집계 테스트, 버전 동기화, 백업 안내 | 핵심 규칙 자동 검증 |
| Phase 1 | 보고 신뢰성 MVP | 보고일 선택기, 기준 배지, Excel 마스킹, 내보내기 감사 | 기준과 개인정보 통제가 화면에 반영 |
| Phase 2 | 보고 확정·데이터 운영 | 스냅샷, 확정·재생성, 백업·복구, 사진 용량 관리 | 과거 보고 결과 재현 가능 |
| Phase 3 | 협업 운영 | RBAC, 사내망 다중 접속, 부서별 처리, 알림 | 역할별 운영 가능 |

#### 우선 개발 순서의 근거

보고일과 마스킹 문제는 현재 업무 오류와 개인정보 노출에 직접 연결되므로 협업 기능보다 먼저 해결합니다. 다중 사용자 기능은 보고 기준과 데이터 보존 정책이 확정된 뒤 진행합니다.

### 제10장. Phase 1 상세 기획

#### 10.1 보고일 선택기

- 목적: 특정 날짜의 일일보고 재현
- 핵심 화면: 전역 보고일 선택, 통보일 기간 표시
- 수용 기준: 일일보고·총괄표·Excel 파일명이 같은 보고일을 사용

#### 10.2 통합 Excel 개인정보 보호

- 목적: 통합 파일의 개인정보 과다 노출 방지
- 기본 정책: 마스킹 적용
- 예외 정책: 원문 포함 시 경고·확인·감사로그 기록
- 수용 기준: 마스킹 여부와 사진 포함 여부를 생성 전에 확인

#### 10.3 보고 스냅샷

- 목적: 생성 시점의 집계 결과를 보존
- 저장 대상: 보고일, 기간, 사용자, 생성 시각, 대상 ID, 집계 결과, 마스킹 설정
- 수용 기준: 원천 데이터 변경 후에도 확정 보고 결과가 변하지 않음

### 제11장. 운영·보안·데이터 관리

#### 포함 내용

- 개인정보 화면·Excel·로그별 노출 원칙
- localhost 기본 바인딩의 장점과 외부 접속 시 추가 요구사항
- DB 파일 백업·복구 절차
- 사진 데이터 용량 관리
- DB 초기화·비밀번호 변경·원문 다운로드의 주의 작업
- 운영 데이터와 샘플 데이터 분리

#### 권장 체크리스트

| 점검 항목 | 확인 내용 |
|---|---|
| 접근 통제 | 세션 만료, 비밀번호 변경, 로그아웃 동작 |
| 데이터 보호 | 운영 DB 미커밋, 정기 백업, 복구 테스트 |
| 다운로드 | 마스킹 기본값, 원문 확인, 생성 이력 |
| 배포 | 포터블 버전 일치, 실행 파일 검증, 포트 충돌 |
| 감사 | 인증·CRUD·설정·내보내기 이벤트 보존 |

### 제12장. 성과 지표와 검증 계획

#### 권장 지표

| 지표 | 정의 | 활용 목적 |
|---|---|---|
| 민원 등록 소요시간 | 자료 확보부터 저장까지 | 입력 효율 평가 |
| HWPX 검수 수정률 | 가져오기 후 수정된 비율 | 파서 품질 개선 |
| 보고서 생성 성공률 | 오류 없이 생성된 비율 | 기능 안정성 평가 |
| 기준 오류율 | 보고일·기간 기준 수정 비율 | Phase 1 효과 확인 |
| 보고 재현율 | 동일 스냅샷 결과 일치율 | Phase 2 효과 확인 |
| 백업 복구 성공률 | 복구 테스트 통과 비율 | 운영 안정성 확인 |
| 비마스킹 다운로드 비율 | 원문 선택 다운로드 비중 | 개인정보 위험 모니터링 |

#### 검증 방법

정량 지표만 사용하지 않고, 담당자 인터뷰와 대표 업무 시나리오 테스트를 함께 진행합니다. 테스트 데이터에는 실제 개인정보를 사용하지 않고 비식별 샘플을 사용합니다.

### 제13장. 결론과 의사결정 요청

#### 결론 구성

- 현재 서비스는 Excel 중심 업무를 SSOT 기반 로컬 서비스로 전환하는 기반을 확보했습니다.
- 현재 가장 큰 개선 기회는 기능 확장이 아니라 보고 신뢰성과 개인정보 통제입니다.
- Phase 1 개발을 승인하면 보고 기준 오류와 다운로드 위험을 먼저 줄일 수 있습니다.
- Phase 2에서 스냅샷·복구를 추가하면 운영 지속성과 감사 대응력이 강화됩니다.

#### 의사결정 요청 예시

1. Phase 1 개발 범위와 우선순위를 승인합니다.
2. 통합 Excel 기본 마스킹 정책을 승인합니다.
3. 보고 스냅샷의 보존 범위와 보존 기간을 결정합니다.
4. 향후 다중 사용자 운영을 위한 권한 모델 검토 시점을 정합니다.

## 5. 부록 구성안

### 부록 A. 용어 정의

`SSOT`, 통보일, 보고일, 미처리, 미정, 포터블, 스냅샷, HWPX를 정의합니다.

### 부록 B. 기능-코드 추적표

| 기능 | 주요 코드 경로 |
|---|---|
| 라우팅 | `src/App.tsx` |
| 레이아웃·기간 | `src/components/AppLayout.tsx` |
| 상태 | `src/store/AuthStore.tsx`, `src/store/ComplaintStore.tsx` |
| 집계 | `src/schema/aggregate.ts` |
| API | `server/index.ts`, `server/auth.ts`, `server/db.ts`, `server/audit.ts` |
| Excel | `src/export/*` |
| HWPX | `src/import/hwpxParser.ts` |
| 배포 | `scripts/build-release.mjs` |

### 부록 C. API와 데이터 모델

현재 API 목록, SQLite 테이블, 주요 `Complaint` 필드, 보고서 집계 규칙을 요약합니다. 구현 상세는 기존 아키텍처·ERD·보고서 스키마 문서로 연결합니다.

### 부록 D. 화면 캡처

`docs/site-snapshots/`의 로그인, 대시보드, 관리대장, 부서별현황, 총괄표, 일일보고, 감사로그, 설정 화면을 기능 설명의 보조 자료로 사용합니다. 캡처에는 실제 개인정보가 없어야 합니다.

### 부록 E. 검증 시나리오

최소한 다음 시나리오를 포함합니다.

1. 민원 1건 등록 후 모든 집계 화면과 Excel에 반영되는지 확인
2. HWPX 여러 건을 가져와 초안 수정 후 일괄 등록
3. 통보일 기간을 변경했을 때 보고 화면과 Excel의 대상 건수 비교
4. 처리 상태별 KPI와 총괄표 기간 버킷 비교
5. 로그아웃·세션 만료·비밀번호 변경 확인
6. 운영 DB 백업 후 별도 디렉터리에서 복구
7. 마스킹·비마스킹 Excel 생성 결과 비교

## 6. 편집·작성 지침

- 현재 구현, 제안 기능, 미구현 항목을 문장 수준에서 명확히 구분합니다.
- 숫자나 성능 지표는 실제 측정값이 있을 때만 기재합니다.
- 운영 데이터와 샘플 데이터를 구분하고 개인정보가 포함된 캡처를 사용하지 않습니다.
- 한 절에는 하나의 핵심 결론만 두고, 세부 근거는 표·도식·부록으로 분리합니다.
- 기술 설명은 사용자 영향과 연결해 작성합니다.
- 로드맵은 기능 나열이 아니라 위험 감소와 업무 가치 순서로 설명합니다.
- 모든 외부 근거와 저장소 문서는 보고서 마지막에 참고문헌으로 정리합니다.
