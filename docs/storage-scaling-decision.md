# 저장 용량·성능 분산 방향 (논의 기록)

> 작성일: 2026-09-17  
> 상태: **방안 5 MVP 구현** (아카이브 전환 · 민원 병합 복원 · 통째 교체)  
> 관련: [사진·민원카드 정책](./photo-hwpx-policy.md) · [아키텍처](./architecture.md) · [ERD](./erd.md) · [개인정보·보안](./privacy-security-policy.md)

본 문서는 DB 비대화로 인한 체감 성능 저하에 대응하기 위한 **저장 전략 선택지**를 심도 있게 정리한다.  
구현 착수 전 합의가 필요한 항목을 명시한다.

---

## 1. 문제 정의

### 1.1 현상

| 관찰 | 설명 |
|---|---|
| DB 파일 비대 | `data/tonghab-minwon.db` 가 수백 MB~GB 규모로 증가 |
| 체감 지연 | 목록 로드·등록·설정(용량 조회)·초기화/VACUUM 등에서 느려짐 |
| 용량 회수 한계 | `DELETE`/`VACUUM`만으로는 **남아 있는 민원·사진 바이트**가 있으면 파일 크기가 거의 줄지 않음 |

### 1.2 원인 (실측·구조)

사진은 `Complaint.photos[].url` 에 `data:image/...;base64,...` 로 임베드되어 SQLite `complaints.data`(JSON 텍스트)에 저장된다.

실측 예시 (로컬 개발 DB, 2026-09-17 전후):

| 항목 | 대략값 |
|---|---|
| 민원 건수 | ~1,200건대 |
| 이미지 장수 | ~3,700장대 |
| JSON 내 사진 payload | 전체의 **약 99%+** |
| JSON 내 텍스트 등 | **수 MB 수준** |

즉, SQLite가 “관계형 메타데이터 저장소”가 아니라 **대용량 바이너리(문자화된 base64) 덤프**에 가깝게 쓰이고 있다.

추가 가중 요인:

1. **base64 오버헤드** (~33% 팽창)  
2. Vault 사용 시 `enc:v1:` 로 사진 문자열 재암호화 → 문자열 길이·CPU 부담 증가  
3. 목록 API가 과거에는 전체 사진을 내려보내 브라우저 메모리·파싱 비용 폭증  
   - 완화됨: 목록은 사진 본문 제거(`listComplaintsLite`), 상세만 로드  
4. HWPX 대량 등록 시 건별 POST + 사진 포함 JSON → 디스크·WAL·암호화 비용 누적

### 1.3 목표

| 목표 | 우선순위 |
|---|---|
| 포터블·단일 PC 운영 단순성 유지 | 필수 |
| 목록·검색·집계 응답성 | 높음 |
| 백업·이전·복구 절차가 현장 담당자에게 이해 가능 | 높음 |
| 현장 확인용 사진 품질 유지 (판독 가능) | 높음 |
| 원본 인쇄급 화질 보존 | **비목표** (정책상 HWPX 원본 미보관) |

| # | 방안 | 결정 |

## 3. 방안 3·4 포기 사유

### 3.1 DB 샤딩 (포기)

- 앱 전제가 **단일 SQLite + 포터블 폴더**다.
- 샤딩 키(연도/부서/동) 설계, **여러 DB를 동시에 열어** 크로스 샤드 집계·검색·엑셀 내보내기하는 구조, 마이그레이션·백업 조합이 급격히 복잡해진다.
- “느림”의 주원인이 행 수가 아니라 **행당 사진 blob**이므로, 샤딩해도 사진이 JSON에 남으면 병목이 이동만 한다.

> **구분**: 아래 **방안 5(아카이브 전환)** 은 “여러 DB를 동시에 조회”하는 샤딩이 아니다.  
> **활성 DB는 항상 하나**이고, 지난 기간은 파일로 보관·필요 시 교체 복원하는 운영 절차다.

### 3.2 외부 스토리지 (포기)

- 오프라인·망분리·내부망 PC 배포와 충돌한다.
- 자격증명·만료·장애 시 사진 유실 리스크, 운영 주체(클라우드 계정) 관리가 현장 부담이다.
- 현재 제품 대비 이득이 작다.

## 4. 방안 1 — 사진 파일 분리 (보류·심층 논의)

### 4.1 개념

```
[현재]
Complaint JSON ── photos[].url = data:image/jpeg;base64,...  ──► SQLite 비대화

[방안 1]
Complaint JSON ── photos[].url = /api/media/{id}/{photoId}.jpg  ──► SQLite는 경로만
                         │
                         └─► data/media/... 실제 JPEG 파일
```

### 4.2 기대 효과

| 효과 | 설명 |
|---|---|
| DB 슬림화 | `complaints.data` 가 텍스트 중심으로 수 MB~수십 MB 수준으로 축소 가능 |
| 목록 성능 | 이미 lite 목록이어도, 상세·갱신·VACUUM·백업 시 SQLite I/O가 크게 감소 |
| 부분 백업·삭제 | 민원 삭제 시 해당 미디어 디렉터리만 제거 가능 |
| 썸네일/원본 이원화 | 필요 시 작은 미리보기·큰 원본을 파일 단위로 분리 설계 가능 |

### 4.3 관리 측면의 어려움 (핵심 논의 포인트)

방안 1은 기술적으로는 명확하나, **운영·관리 복잡도**가 올라간다. 합의 없이 착수하지 않는다.

#### (A) 백업·이전 단위가 둘로 갈라짐

| 현재 | 방안 1 |
|---|---|
| `data/tonghab-minwon.db` (+ WAL) 복사면 사실상 전체 | DB + **`data/media/` 트리** 동시 백업 필수 |
| 포터블 안내: “data 폴더 복사”로 퉁칠 수 있음 | 안내·체크리스트·누락 시 **사진은 없고 메타만 있는** 깨진 상태 가능 |

논의 질문:

- 백업 단위를 항상 `data/` 전체로 고정할 것인가?
- DB만 복사했을 때 앱이 어떻게 경고할 것인가? (미디어 누락 감지)

#### (B) 정합성 (orphan / dangling)

| 리스크 | 내용 |
|---|---|
| orphan 파일 | DB 레코드는 삭제됐는데 파일만 남음 → 디스크 누수 |
| dangling 참조 | DB에 경로가 있는데 파일 없음 → UI 깨짐·엑셀 내보내기 실패 |
| 부분 실패 | 파일 기록 성공 후 DB 커밋 실패(또는 반대) |

필요 운영 도구(도입 시):

- 미디어 정합성 점검(설정 화면)
- 고아 파일 청소
- 누락 파일 리포트

#### (C) 포터블·권한·경로

- Windows 포터블에서 `data/media` 경로·권한·백신 실시간 검사로 **다수 소파일 I/O**가 느려질 수 있다.
- `TM_DATA_DIR` 변경 시 media 루트도 함께 이동해야 한다.
- 네트워크 드라이브에 `data`를 둘 경우 파일 수 증가로 latency가 더 도드라질 수 있다.

#### (D) 보안·암호화

| 현재 | 방안 1 |
|---|---|
| Vault 켜면 사진 data URL 문자열이 DB 안에서 암호화 | 파일을 **평문 JPEG로 둘지 / 파일 단위 암호화할지** 추가 결정 필요 |
| 단일 DB ACL·파일 권한 | media 디렉터리 ACL, 유출 시 이미지 직접 열람 가능 여부 |

논의 질문:

- Vault ON일 때 media 파일도 DEK로 암호화할 것인가? (복호화 스트리밍·성능 비용)
- 인증된 `/api/media` 만으로 충분한가? (디스크 직접 접근 위협 모델)

#### (E) 기존 데이터 마이그레이션

- 이미 DB에 들어간 base64/enc 사진을 파일로 **일괄 추출**하는 배치가 필요하다.
- 마이그레이션 중 용량 일시 증가(DB + 파일 공존), 실패 재실행, 진행률 UI.
- 마이그레이션 전 필수 백업 절차.

#### (F) 내보내기·감사·API 계약

- 엑셀 이미지 삽입: data URL이 아니라 media URL → 서버에서 바이트를 읽어 buffer로 변환하는 경로 필요.
- 감사 로그에 이미지 본문을 넣지 않는 현 정책은 유지 가능하나, 경로 변경을 문서화해야 한다.
- 목록 lite 정책: media 경로는 짧아 **목록에 썸네일 URL을 남겨도** DB/응답이 가벼워지는 이점이 있다 (방안 1의 추가 이득).

### 4.4 방안 1을 택할 경우의 최소 설계 원칙 (초안, 미채택)

합의 시에만 유효한 초안이다.

1. SSOT는 계속 **관리대장 Complaint**. 사진 파일은 Complaint에 종속.  
2. 백업 SSOT는 **`TM_DATA_DIR`(기본 `data/`) 전체**.  
3. API로만 media 제공 (`requireAuth`).  
4. 삭제·초기화 시 media도 함께 정리 + 정합성 점검 메뉴.  
5. Vault 정책은 보안 문서와 동일 개정으로 확정.

### 4.5 방안 1 논의 체크리스트

- [ ] 현장 백업 담당자 절차: `data/` 통째 복사로 충분한가?  
- [ ] Vault ON 시 파일 암호화 범위  
- [ ] 마이그레이션 창구(설정 메뉴)와 실패 복구  
- [ ] 포터블 배포 `사용방법.txt` / `data/README.txt` 개정  
- [ ] 개인정보 영향평가·보안 검토 필요 여부

## 5. 방안 2 — 임베드 유지 + 압축 강화 (현행·QA 필요)

### 5.1 개념

저장 모델은 유지한다 (`photos[].url` 임베드).  
HWPX 반입 시 브라우저 canvas로 JPEG 재인코딩하여 **저장 직전 바이트를 줄인다.**

### 5.2 현재 구현 (코드 기준 2026-09-17)

구현 위치: `src/import/hwpxParser.ts` → `compressImage`

| 항목 | 값 |
|---|---|
| 1차 | 긴 변 최대 **640px**, JPEG quality **0.55**, data URL 길이 목표 ≤ ~90KB |
| 초과 시 | scale·quality 단계적 하향 (하한 quality ~0.35) |
| 1차 실패 시 | 긴 변 **480px**, quality **0.4** 재시도 |
| 최종 실패 시 | 원본 MIME base64 폴백 (비권장 경로, 용량 위험) |
| 스케일 기준 | **긴 변(max(width,height))** — 과거 width-only 버그 수정 |

참고: 과거 정책 문서의 `720px / 0.72` 는 구버전이다. 본 문서·QA 결과가 확정되면 [photo-hwpx-policy.md](./photo-hwpx-policy.md) 를 갱신한다.

### 5.3 장점·한계

| 장점 | 한계 |
|---|---|
| 백업·배포 모델 불변 (`data` 한 덩어리) | 사진이 계속 DB 안에 있음 → **구조적 병목 잔존** |
| 구현·운영 단순 | 이미 적재된 대용량 데이터는 **재가져오기/재압축 마이그레이션 없이는** 안 줄어듦 |
| 포터블 안내 변경 최소 | Vault 암호화·base64 오버헤드는 남음 |
| | 과도한 압축 시 **판독 품질** 저하 리스크 |

### 5.4 품질 보증(QA) 검증 계획 — **필수**

방안 2를 “기본 정책”으로 확정하려면 아래 검증을 통과해야 한다.  
(미검증 상태로 파라미터를 더 낮추지 않는다.)

#### (A) 판독성 (업무 품질)

샘플 유형별 **최소 20장** (가능하면 실카드 HWPX):

| 유형 | 확인 포인트 |
|---|---|
| 원거리 현장 | 차량번호·간판·표지판 문자 판독 |
| 근거리 파손/투기 | 상태 식별 가능 여부 |
| 야간·그늘 | 노이즈·뭉개짐 |
| 세로·가로 혼합 | 긴 변 리사이즈 후 비율·잘림 |
| 처리전/후 쌍 | 동일 지점 비교 가능 여부 |

판정 기준(초안):

- **합격**: 담당자가 보고서·현황 공유 목적으로 “쓸 만하다”고 합의  
- **조건부**: 특정 유형만 파라미터 완화(예: 긴 변 720 유지)  
- **불합격**: 차량번호·표지 등 핵심 식별 정보가 반복적으로 소실 → 640/0.55 재조정

#### (B) 용량·성능

| 지표 | 측정 방법 | 목표(초안) |
|---|---|---|
| 장당 data URL 크기 | 반입 직후/저장 직전 | 중앙값 ≤ 100KB, p95 ≤ 150KB 수준 |
| 민원 1건(사진 3장) | 설정 화면 사진 payload | 구버전(720/0.72) 대비 명확한 감소 |
| 500건 등록 | 백그라운드 job 완료 시간·API 오류율 | 오류 없이 완료, 체감 개선 |
| 목록 최초 로드 | 빈 캐시 | 사진 lite 유지 전제, 회귀 없음 |

#### (C) 회귀·예외

| 항목 | 확인 |
|---|---|
| 압축 실패 폴백 | 원본 대용량이 대량 유입되지 않는지 (경고·건수) |
| Vault ON/OFF | 저장·조회·엑셀 이미지 삽입 |
| 엑셀 내보내기 | `includeImages` 시 깨짐·과도한 용량 |
| 동일 카드 재등록 | importKey(지문) 갱신 시 사진 교체 |

#### (D) QA 산출물

- [ ] 샘플 세트 목록(파일명·유형)  
- [ ] Before/After 스크린샷 또는 나란히 비교표  
- [ ] 파라미터 최종값 (`maxEdge`, `quality`, `maxBytes`)  
- [ ] “기존 DB 재압축을 할지” 별도 결정 (권장: 필요 시 배치, 기본은 신규만)

### 5.5 방안 2와 이미 적용된 완화책의 관계

압축과 별개로 이미 적용·유지해야 할 성능 완화:

| 완화 | 상태 |
|---|---|
| 목록 API 사진 본문 제거 | 유지 |
| 상세 조회 시에만 사진 로드 | 유지 |
| 백그라운드 건별 등록 + 전역 진행 배너 | 유지 |
| 설정 화면 용량·사진 payload 구분 표시 | 유지 |
| DB 초기화 시 VACUUM / 용량 회수 | 유지 (빈 공간만 회수) |

방안 2만으로 “수천 건 × 다사진”을 무한히 버티게 만들 수는 없다.  
QA 합격 후에도 한도(권장 건수·디스크)를 운영 가이드에 적을 것을 권한다.  
**기간·연도 단위로 방안 5를 쓰면** 활성 DB 크기를 현실적으로 리셋할 수 있다.

## 6. 방안 5 — 관리연도·기간 한정: 아카이브 백업 + 신규 DB 전환

### 6.1 한 줄 평가

**권고에 가깝다.** 포기한 “샤딩(다중 DB 동시 운용)”과 달리, **활성은 항상 단일 DB**를 유지하면서 용량·성능 한도를 **행정 주기(연도·캠페인)** 로 끊는 운영 패턴이다. 포터블·백업 단순성과도 잘 맞는다.

### 6.2 개념

```
[전환 전]
data/tonghab-minwon.db          ← 활성 (예: 2025 관리연도, 비대)

[전환 실행]
1) WAL 체크포인트 후 파일 안전 복사/이동
2) data/archives/tonghab-minwon-2025.db  (+ 선택: .meta.json 라벨)
3) 빈 스키마로 신규 tonghab-minwon.db 생성
4) 계정·설정 등 유지 정책에 따라 seed (아래 §6.4)

[전환 후]
활성 DB = 작음 → 목록·등록 체감 회복
과거 조회 = 아카이브 파일을 “복원(교체)”하거나 외부에서만 열람
```

기간 한정 사업도 동일: 종료일 → 아카이브 → 신규(또는 다음 기간용) DB.

### 6.3 왜 방안 3(샤딩)과 다른가

| | 샤딩 (포기) | 아카이브 전환 (방안 5) |
|---|---|---|
| 동시 open | 연도별 DB 여러 개 | **활성 1개만** |
| 집계·검색 | 크로스 샤드 필수 | 활성 기간만 (과거는 복원 후) |
| 구현 복잡도 | 높음 | 파일 rename/copy + 스키마 초기화 수준 |
| 현장 이해 | “어느 DB가 진짜?” | “올해 DB / 작년 보관본” |

### 6.4 현재 `DB 초기화(reset-seed)` 와의 차이

| | reset-seed (현행) | 아카이브 전환 (확정 방향) |
|---|---|---|
| 과거 민원 | **삭제** (샘플로 교체) | **archives/ 파일로 보존** 후 활성 민원만 비움 |
| 보고 스냅샷 | 삭제 | **활성에 유지** |
| 감사 로그 | 삭제 | **활성에 유지** |
| 계정·2FA·설정 | 유지 | **활성에 유지** (전환 직후 동일) |
| 용도 | 개발·테스트·완전 비우기 | **연도·분기·기간 마감** |

즉 활성 DB의 로그인·2FA·Vault는 전환 후에도 그대로 이어지고, 이후 비밀번호 변경·2FA 재발급도 **활성 DB에만** 반영된다.  
보관본 파일은 **전환 시점의 동결본**이다.

### 6.5 기대 효과

| 효과 | 설명 |
|---|---|
| 성능 리셋 | 활성 DB가 작아져 목록·상세·VACUUM·용량 조회가 다시 가벼워짐 |
| 백업 명확화 | `archives/…-2025.db` = 그해 스냅샷. USB·외장 복사 안내가 쉬움 |
| 방안 1 없이도 한도 관리 | 파일 분리 전에도 “연 단위로 끊기”로 운영 가능 |
| 방안 2와 보완 | 신규 연도는 압축 강화분부터 쌓임; 구연도는 압축 안 해도 아카이브로 격리 |

### 6.6 설계 시 반드시 정할 것 (논의 포인트)

#### (A) 무엇이 활성에 남나 (확정)

| 유지 (활성) | 비움 (활성) | 보관본에만 |
|---|---|---|
| `users` (비번·2FA) | `complaints` | 전환 시점의 민원 전체(+당시 users/vault 상태 포함 파일) |
| `app_settings` (Vault salt/verifier·TTL 등) | — | |
| `report_snapshots` | — | |
| `audit_logs` | — | |

#### (B) 아카이브 보관 위치·이름

- 권장: `data/archives/tonghab-minwon-{label}.db`  
  - `label` 예: `2025`, `2025Q1`, `캠페인명_20260301-20260831`
- WAL/SHM: 복사 전 `PRAGMA wal_checkpoint(TRUNCATE)` 후 **본편 `.db`만** 아카이브.
- `data/README.txt` / 포터블 `사용방법.txt`에 “백업 = data 전체(archives 포함)” 명시.

#### (C) 과거 데이터 다시 보기

|---|---|---|
| MVP | 아카이브 목록 + **「이 보관본으로 전환(활성 교체)」** + 현재 활성은 임시 백업 | 낮음 |
| 다음 | 보관본 **민원만 병합 복원**(활성 계정·Vault 유지) — §6.7 필수 | 중 |

#### (D) 안전장치

- 전환 전 **비밀번호(+2FA)** 확인 (reset-seed와 동일 급).
- 디스크 여유 공간 검사 (아카이브 복사본 크기만큼).

- “관리 기간” 시작·종료일을 설정에 두고, 종료 임박 시 배너로 전환 유도 (강제 잠금은 선택).

### 6.7 복원 × 비밀번호 변경 × 2FA 재발급 (중요)

Vault DEK는 **로그인 비밀번호 + `app_settings`의 salt** 로 유도되고, 비밀번호 변경 시 `rotateVaultPassword`가 **활성 DB의** 민원·TOTP 시크릿을 새 키로 재암호화한다.  
아카이브 파일은 그 이후 **자동으로 갱신되지 않는다.**

타임라인 예:

```
T0  아카이브 생성 (민원·당시 users·vault_salt/verifier 동결)
T1  활성에서 분기 신규 입력 시작 (민원만 빈 상태, 계정은 유지)
T2  활성에서 비밀번호 변경 및/또는 2FA 재등록
T3  보관본 복원 시도
```

#### (1) 복원 = 보관본 파일로 활성 DB **통째 교체**

| 항목 | 결과 |
|---|---|
| 로그인 비밀번호 | **T0 당시 비밀번호**로만 로그인. T2의 새 비밀번호는 무효 |
| 2FA | 보관본의 TOTP 시크릿(및 복구코드) 기준. T2에 재발급한 앱 코드와 **불일치** |
| Vault | 보관본 salt/verifier = T0 키. T0 비밀번호로 unlock |
| T1 이후 활성에만 있던 신규 민원 | **소실**(교체 전 활성 백업을 안 남기면) |

→ “가끔 작년 DB로 바꿔 본다”에는 단순하지만, **교체 후 인증 상태가 과거로 되돌아간다**는 점을 UI에 반드시 경고해야 한다.

#### (2) 복원 = 활성 계정·Vault는 유지하고 **민원만 병합**

| 항목 | 결과 |
|---|---|
| 로그인·2FA | **문제 없음** (활성 `users` 유지) |
| Vault OFF / 비번 변경 없음 | 보관본 민원 ciphertext가 활성 DEK와 동일 → 병합 가능 |
| Vault ON + T2 비밀번호 변경 | 보관본 민원은 **옛 DEK**로 암호화됨. 활성은 **새 DEK**. 그대로 INSERT하면 **복호화 실패** |
| 필요 절차 | 복원 마법사: (a) 보관본 열 때 **아카이브 시점 비밀번호** 입력 → 옛 DEK로 unseal → (b) 활성 현재 DEK로 재 seal 후 활성에 삽입 |

→ 운영상 “분기 중 비번·2FA를 바꿔도 된다”를 허용하려면 **병합 복원 + 재암호화 경로**가 맞다. 통째 교체만 있으면 T2 이후 복원이 위험하다.

#### (3) 2FA만 재발급하고 비밀번호는 그대로

| 복원 방식 | 결과 |
|---|---|
| 통째 교체 | 보관본의 옛 TOTP로 돌아감. 새 인증기 코드 불일치 → **옛 OTP 또는 당시 복구코드** 필요 |
| 민원만 병합 | 활성 2FA 유지 → **문제 없음**. (Vault 키 동일하므로 암호문도 호환) |

#### (4) 권고 정책 (복원 기능 설계 시)

1. **일상 운영**: 아카이브 이후 비밀번호·2FA 변경은 활성에서 자유롭게 허용 (현 구조와 맞음).  
2. **복원 UX 기본값**: 「민원만 가져오기(병합)」 + Vault ON이면 **보관 시점 비밀번호**를 한 번 더 받아 재암호화.  
3. 「보관본으로 통째 교체」는 고급/위험 옵션으로 두고, **로그인·2FA·Vault가 보관 시점으로 되돌아감**·**현재 분기 민원 백업 필수**를 확인 문구로 강제.  
4. 보관본 메타(`.meta.json` 등)에 `archivedAt`, `vaultEnabled`, `label`을 남겨 복원 UI가 분기할 수 있게 한다.  
5. 통째 교체 전에 현재 활성을 `archives/before-restore-….db`로 자동 백업.

### 6.8 리스크·한계

| 리스크 | 완화 |
|---|---|
| 아카이브 파일 분실 = 그해 데이터 소실 | 외장 추가 복사 안내, 전환 UI에 경로 표시 |
| “작년 통계와 올해를 한 화면” 요구 | 제품 비범위로 못 박거나 엑셀을 연도별로 내보내 보관 |
| Vault 키(당시 비번) 분실 시 보관본 민원 복호화 불가 | 복원 시 당시 비번 필요 고지; 보안 문서와 연계 |
| 통째 교체 시 인증 롤백·신규 분기 데이터 소실 | §6.7 경고 + 교체 전 자동 백업 |
| 비밀번호 변경 후 민원 병합 시 키 불일치 | 재암호화 병합 경로 필수 |
| 디스크에 연도별 DB 누적 | 오래된 아카이브는 외장 이관 후 로컬 삭제 가이드 |
| 전환 중 전원 끊김 | checkpoint + 복사 확인 후 DELETE, 실패 복구 문서화 |
| Windows 파일 권한 | `copyFileSync`는 Unix `chmod` 없음. 보관본은 `data/archives/` ACL 상속 → 활성 DB와 동일 계정으로 읽기·쓰기. 다른 Windows 계정·잠긴 USB/네트워크 드라이브만 주의 |

### 6.9 기존 기능과의 역할 분담 (권고)

| 기능 | 역할 |
|---|---|

### 6.10 구현 MVP 스케치 (합의 후)

설정 화면 예시:

1. **보관 라벨** 입력 (기본: 올해 연도/분기)  
2. 미리보기: 현재 DB 경로·크기·민원 건수  
3. 실행 → `archives/` 복사 → 활성 `complaints`만 DELETE → VACUUM  
   - 스냅샷·감사·유저·Vault 설정 **유지**, 샘플 민원 **미삽입**  
4. **보관본 관리**: 목록·크기  
   - 1차: 통째 교체(위험 경고)  
   - 권장 후속: 민원 병합 + (Vault 시) 당시 비번으로 재암호화  

코드 위치 후보: `server/db.ts`, `server/vault.ts`(병합 재암호화), `server/index.ts` API, `SettingsPage` UI.
