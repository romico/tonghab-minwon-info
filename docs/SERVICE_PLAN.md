## 1. 기획 요약

통합민원정보는 전주시 생활민원 담당자가 민원 원천 데이터를 한 곳에서 관리하고, 그 결과를 부서별 현황·총괄표·일일보고·대시보드로 즉시 확인하고 Excel로 배포할 수 있게 하는 **로컬 우선 민원 업무 서비스**입니다. 현재 서비스의 가장 중요한 설계 결정은 관리대장만을 쓰기 원천으로 두고, 나머지 보고서를 조회 시점에 파생하는 것입니다. 이 구조는 여러 Excel 파일의 수식과 복사 오류를 줄이고 보고서 간 숫자 불일치를 방지합니다.

현재 구현은 단일 관리자와 단일 PC 운영에 최적화된 0.x 버전입니다. 따라서 다음 개발 단계는 기능을 무작정 확장하기보다 **보고 기준일을 명시적으로 선택하고, 확정된 보고 결과를 보존하며, 개인정보가 포함된 내보내기를 통제하는 것**에 집중해야 합니다. 이 세 가지가 해결되면 서비스는 단순한 Excel 대체 도구에서 반복 가능한 민원 보고 업무 시스템으로 발전할 수 있습니다.

> **제품 방향:** 입력은 한 번, 집계는 일관되게, 보고는 검증 가능하게, 데이터는 안전하게.

## 2. 서비스 배경과 문제 정의

### 2.1 대상 업무

민원 담당자는 접수된 생활민원을 관리대장에 기록하고, 처리 부서와 상태를 갱신한 뒤, 같은 원천 데이터를 여러 보고 양식으로 재구성합니다. 기존 업무는 Excel 관리대장, 부서별 현황, 총괄표, 일일보고를 함께 운영하는 방식에 의존합니다.

### 2.2 현재 문제

| 문제 | 업무 영향 | 서비스 대응 |
|---|---|---|
| 여러 보고 시트의 수식·복사 의존 | 보고서별 숫자가 달라지고 오류 원인 추적이 어려움 | 관리대장 SSOT와 조회 시점 집계 |
| 수동 일일보고 작성 | 통보일과 보고일을 잘못 적용할 가능성 | 경로×분야 매트릭스 자동 계산 |
| 민원카드와 사진의 재입력 | 입력 시간이 길고 누락이 발생 | HWPX 다중 가져오기와 초안 검수 |
| 담당 PC마다 실행 환경이 다름 | 설치·업데이트·장애 대응 비용 발생 | Node 런타임 포함 Windows 포터블 |
| 민원인 개인정보가 보고서에 포함 | 화면·다운로드·공유 과정에서 과다 노출 위험 | 화면 기본 마스킹과 Excel 선택 마스킹 |
| 보고 결과가 조회 시점에만 존재 | 나중에 당시 보고 숫자를 재현하기 어려움 | 향후 보고 스냅샷·확정 기능 필요 |

## 3. 서비스 목표와 비목표

### 3.1 목표

1. 담당자가 민원 한 건을 한 번만 입력하거나 가져오면 모든 현황 화면과 보고서에 일관되게 반영한다.
2. 통보일·보고일·처리 상태의 의미를 화면에서 명확히 보여 주어 보고 기준 오류를 줄인다.
3. HWPX 원본을 보관하지 않고도 민원카드의 핵심 필드와 사진을 빠르게 등록한다.
4. 담당자가 Excel을 생성·검토·공유하는 과정을 안전하게 수행하도록 마스킹과 감사 이력을 제공한다.
5. Windows 포터블 배포를 유지하면서 데이터 백업·복구와 버전 업데이트를 이해하기 쉽게 만든다.
6. 향후 다중 사용자나 사내망 운영으로 확장할 수 있도록 현재의 인증·감사·도메인 경계를 정리한다.

### 3.2 비목표

현재 단계에서는 클라우드 멀티테넌시, 모바일 네이티브 앱, 외부 민원 접수 채널 연계, 복잡한 조직별 권한 체계, 실시간 다중 PC 동시 편집을 목표로 하지 않습니다. 이러한 기능은 단일 PC 운영의 안정성과 보고 기준이 먼저 고정된 뒤 별도 제품 단계로 검토합니다.

## 4. 사용자와 핵심 과업

| 사용자 | 주요 책임 | 대표 과업 | 가장 중요한 성공 조건 |
|---|---|---|---|
| 민원 담당자 | 원천 데이터 입력·정리·보고 | HWPX 가져오기, 민원 보완, 기간별 현황 확인 | 빠른 입력과 낮은 재작업 |
| 보고 작성자 | 일일·총괄 보고 생성·검증 | 보고일 설정, 집계 확인, Excel 생성 | 숫자의 재현성과 기준일 명확성 |
| 관리자 | 운영·보안·데이터 관리 | 비밀번호·세션 설정, 감사로그, 백업·초기화 | 변경 추적과 복구 가능성 |
| 검토자/상급자 | 결과 확인 | 대시보드·보고서 검토 | 핵심 KPI와 미처리 우선순위 파악 |

현재 구현은 단일 `admin` 계정 중심이므로 위 역할은 실제 권한이 아니라 업무 역할입니다. 역할별 접근 제어는 향후 RBAC 단계에서 도입합니다.

### 4.1 핵심 Job-to-be-Done

> 민원 담당자는 접수 자료가 들어왔을 때, 원본을 다시 입력하는 시간을 줄이면서도 필요한 정보를 검수한 뒤, 같은 숫자의 보고서를 정해진 기준일에 만들어야 한다.

> 보고 작성자는 특정 보고일의 처리 현황을 확인할 때, 어떤 데이터가 집계되었는지 설명할 수 있고 나중에도 같은 결과를 다시 확인할 수 있어야 한다.

> 관리자는 운영 PC가 바뀌거나 오류가 발생했을 때, 개인정보와 업무 데이터를 잃지 않고 안전하게 이전할 수 있어야 한다.

## 5. 서비스 구조와 핵심 경험

### 5.1 정보 구조

```text
로그인
  └─ 대시보드: 전체 현황·미처리 우선순위·통합 Excel
      ├─ 관리대장: 유일한 입력·수정·삭제 원천
      │   └─ 수동 등록 / HWPX 가져오기 / 사진 / 상태 갱신
      ├─ 부서별현황: 부서별 건수·완료·미처리·처리율
      ├─ 총괄표: 처리 개요·기간 버킷·경로·분야·실국
      ├─ 일일보고: 보고일 기준 경로×분야·동별 집계
      ├─ 감사로그: 인증·민원·설정 변경 이력
      └─ 설정: 세션·비밀번호·시드 초기화
```

### 5.2 기준 데이터 흐름

`Complaint`가 관리대장의 쓰기 모델입니다. 화면은 `/api/complaints`를 통해 데이터를 읽고 쓰며, 클라이언트의 `ComplaintStore`가 통보일 기간으로 필터링한 뒤 `src/schema/aggregate.ts`의 집계 함수를 호출합니다. 보고 화면과 Excel은 이 동일한 파생 결과를 사용합니다.

이 구조를 유지하되, 집계 결과를 재현해야 하는 시점에는 다음 메타데이터를 함께 저장해야 합니다.

| 메타데이터 | 필요 이유 |
|---|---|
| 보고일 | 일접수와 처리기간 계산 기준 |
| 통보일 기간 | 대상 민원 범위 재현 |
| 생성 시각 | 보고 생성 시점 확인 |
| 데이터 버전 또는 대상 ID 목록 | 원천 데이터 변경 전후 구분 |
| 마스킹 설정 | 다운로드 개인정보 노출 수준 확인 |
| 생성 사용자 | 책임 추적 |

## 6. 현재 서비스 평가

### 6.1 강점

- **단일 원천 모델:** 관리대장만 수정하므로 보고서 간 중복 저장이 없습니다.
- **업무 양식 친화성:** 기존 관리대장·부서별현황·총괄표·일일보고를 화면과 Excel로 유지합니다.
- **현장 배포성:** Node 런타임을 포함한 Windows 포터블 ZIP으로 별도 설치 부담이 낮습니다.
- **가져오기 검수 흐름:** HWPX를 바로 확정하지 않고 초안으로 보여 주어 휴리스틱 오분류를 수정할 수 있습니다.
- **운영 추적 기반:** 로그인, 민원 변경, 설정 변경, 초기화 이벤트를 감사로그에 남깁니다.
- **개인정보 기본 보호:** 화면 기본 마스킹과 사진·민원카드 처리 정책이 분리되어 있습니다.

### 6.2 주요 리스크와 한계

| 우선순위 | 리스크 | 현재 상태 | 대응 방향 |
|---|---|---|---|
| P0 | 보고일 선택 UI 부재 | `reportDate`는 오늘 또는 localStorage 값에 의존 | 전역 보고일 선택기와 기준일 표시 도입 |
| P0 | 보고 결과 확정 불가 | 스냅샷 API·freeze 미구현 | 보고서 생성 시 스냅샷 저장·조회 |
| P0 | 통합 Excel 마스킹 제어 부족 | 통합 내보내기 기본값이 개인정보 포함 가능 | 기본 마스킹, 명시적 해제, 경고·감사 |
| P1 | 단일 계정 | RBAC·사용자 관리 없음 | 역할 모델과 계정 관리 설계 |
| P1 | 사진을 JSON data URL로 저장 | DB와 요청 본문이 커질 수 있음 | 용량 경고, 이미지 저장 분리 검토 |
| P1 | 내보내기 자체의 감사 부족 | CRUD 중심으로만 기록 | `EXPORT_*` 이벤트와 파일 메타데이터 기록 |
| P2 | 포터블 버전 표기 불일치 가능 | 패키징 스크립트와 루트 버전 동기화 필요 | 빌드 시 단일 버전 원천 사용 |
| P2 | 자동화 테스트 부족 | `package.json`에 별도 테스트 스크립트 없음 | 집계·파싱·내보내기 핵심 테스트 추가 |

## 7. 제품 전략

### 전략 1. 입력보다 보고 신뢰성을 우선한다

입력 편의성은 HWPX 가져오기와 일괄 등록으로 이미 기반이 있습니다. 다음 경쟁력은 “이 숫자가 어느 기준으로 계산되었는가”를 설명하는 것입니다. 모든 보고 화면에 보고일, 통보일 기간, 대상 건수를 표시하고, 보고 확정본은 변경 후에도 보존해야 합니다.

### 전략 2. 로컬 우선은 유지하되 데이터 이동성을 제품 기능으로 만든다

단일 파일 DB와 포터블 운영은 현장 제약에 적합합니다. 그러나 파일 복사만으로 백업을 설명하면 사용자가 실수할 수 있으므로 백업 시점, 파일 무결성, 복구 확인, 버전 호환성을 제품 흐름에 포함해야 합니다.

### 전략 3. 개인정보 보호를 다운로드 중심으로 강화한다

화면 마스킹만으로는 Excel 공유 위험을 충분히 줄일 수 없습니다. 특히 통합 보고서는 여러 데이터를 한 파일에 담으므로 기본 마스킹과 다운로드 전 확인을 적용해야 합니다. 마스킹 해제는 관리자 확인과 감사 대상이 되어야 합니다.

| 가져오기 품질 표시 | HWPX 휴리스틱 오분류를 빠르게 확인 | 필드별 신뢰도·필수 검수 표시 |

### Phase 3 — 협업 운영 (P2)

| 기능 | 사용자 가치 | 전제 |
|---|---|---|
| 사용자·역할 관리 | 담당·검토·관리 책임 분리 | 세션·권한 모델 확정 |
| 사내망 다중 접속 | 여러 담당자가 동일 원천 사용 | 동시성·백업·HTTPS 검토 |
| 부서별 처리 요청 | 담당 부서가 자기 건을 갱신 | RBAC와 변경 이력 필요 |

## 9. Phase 1 상세 기능 기획

### 9.1 보고일 선택기

**목적:** 오늘이 아닌 특정 날짜의 일일보고를 정확히 재현합니다.

**사용 흐름:** 사용자가 전역 보고일을 선택하면 일일보고의 일접수, 총괄표의 처리기간 계산, 관련 Excel 파일명이 같은 보고일을 사용합니다. 화면에는 `보고일: YYYY-MM-DD`를 항상 표시하고, 기간 필터는 별도의 `통보일 기간: YYYY-MM-DD ~ YYYY-MM-DD`로 표시합니다.

**수용 기준:**

- 보고일은 유효한 날짜만 선택할 수 있습니다.
- 일일보고의 일접수 건수는 `notifiedAt === reportDate` 규칙으로 계산됩니다.
- 보고일을 변경하면 화면·Excel·파일명에 동일한 값이 반영됩니다.
- 새로고침 후에도 선택한 보고일이 유지됩니다.
- 보고일과 통보일 기간이 다르다는 점을 문구로 구분합니다.

### 9.2 통합 Excel 개인정보 보호

**목적:** 통합 보고서 생성 시 개인정보가 기본적으로 과다 포함되지 않도록 합니다.

**정책:** 기본값은 마스킹입니다. 사용자가 원문 포함을 선택하는 경우 경고를 표시하고, 사용자·시각·보고일·파일 종류·마스킹 여부를 감사로그에 기록합니다. 사진 포함 여부도 별도 선택으로 둡니다.

**수용 기준:**

- 통합 Excel은 기본적으로 이름·전화번호 등 정책 대상 필드를 마스킹합니다.
- 원문 포함을 선택하지 않으면 원문 개인정보가 생성 파일에 들어가지 않습니다.
- 원문 다운로드 전 확인 단계가 있습니다.
- 감사로그에서 내보내기 조건을 확인할 수 있습니다.

### 9.3 보고 스냅샷

**목적:** 보고서가 생성된 시점의 결과를 나중에 재현합니다.

**저장 원칙:** 전체 민원 본문을 중복 저장하기보다 보고 메타데이터와 대상 민원 ID·집계 결과·생성 버전을 우선 저장합니다. 개인정보가 포함된 파일 자체를 서버에 자동 보관하는 것은 별도 보안 검토 없이는 하지 않습니다.

**수용 기준:**

- 사용자는 보고일·통보일 기간·생성자·생성 시각으로 스냅샷을 조회할 수 있습니다.
- 확정된 스냅샷은 원천 데이터가 변경되어도 결과 숫자가 바뀌지 않습니다.
- 재생성 시 기존 스냅샷을 덮어쓰지 않고 새 이력으로 남깁니다.
- 스냅샷과 실제 Excel 파일의 보관 정책이 구분됩니다.

## 10. 핵심 지표와 운영 측정

| 지표 | 정의 | 초기 목표 방향 |
|---|---|---|
| 신규 민원 등록 소요시간 | 자료 확보부터 저장 완료까지의 시간 | HWPX 사용 시 수동 입력 대비 감소 |
| 가져오기 검수율 | HWPX 가져오기 후 수정 없이 등록된 비율 | 추세를 측정하되 정확도 우선 |
| 보고서 생성 성공률 | 오류 없이 생성된 내보내기 비율 | 99%에 근접 |
| 보고 기준 오류율 | 보고일·기간 기준 수정이 발생한 보고 비율 | Phase 1 이후 지속 감소 |
| 보고서 재현율 | 같은 스냅샷을 조회했을 때 결과가 동일한 비율 | Phase 2 이후 100% |
| 미처리 민원 경과시간 | 통보일부터 완료·예정일까지의 경과 | 부서별 개선 추세 확인 |
| 백업 복구 성공률 | 테스트 복구에서 데이터 검증을 통과한 비율 | 정기 점검에서 100% |
| 개인정보 비마스킹 다운로드 비율 | 전체 Excel 생성 중 원문 선택 비율 | 권한·업무 필요성 기준으로 모니터링 |

지표 수집은 개인정보를 추가로 저장하지 않는 방향으로 설계합니다. 사용자 행동 로그를 확대할 때는 목적, 보관 기간, 접근 권한을 먼저 정합니다.

## 11. 운영·보안 원칙

1. 운영 데이터와 샘플 데이터를 분리합니다.
2. `data/tonghab-minwon.db`와 실제 민원 자료는 Git에 커밋하지 않습니다.
3. 기본 바인딩은 `127.0.0.1`을 유지하고 외부 접속을 허용할 때 HTTPS·인증·방화벽을 함께 검토합니다.
4. 비밀번호 변경·DB 초기화·원문 Excel 다운로드는 높은 주의가 필요한 작업으로 취급합니다.
5. HWPX는 가져오기 후 원본을 저장하지 않는 현재 정책을 유지하되, 사용자가 검수 결과를 확인할 수 있게 합니다.
6. 사진과 개인정보는 화면·Excel·로그에서 노출 범위를 다르게 적용합니다.
7. 백업은 파일 복사만 안내하지 않고 복구 테스트까지 포함합니다.

## 13. 결론

통합민원정보는 이미 업무의 핵심 문제인 **중복 보고 작성과 실행 환경 의존성**을 해결하는 방향으로 구현되어 있습니다. 제품 완성도를 높이는 다음 단계는 화면을 더 늘리는 것이 아니라, 보고 기준을 명시하고 결과를 보존하며 개인정보 다운로드를 통제하는 것입니다. Phase 1의 보고일 선택기·기준 정보 표시·통합 Excel 마스킹·내보내기 감사 이벤트를 먼저 완료하면 사용자는 서비스 결과를 더 신뢰할 수 있고, 운영자는 문제 발생 시 원인을 추적할 수 있습니다. 이후 보고 스냅샷과 복구 도구를 추가하면 단일 PC용 도구에서 지속 가능한 행정 업무 서비스로 확장할 수 있습니다.
